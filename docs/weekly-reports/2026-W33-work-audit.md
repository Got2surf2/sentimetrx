## 3. What we introduced that still needs addressing

**⚠️ a. The entity-counts change is unverified against real data.** Dropping the `singleDataset` gate means multi-member collections above the cap now return **sampled** counts where they previously returned exact ones — a real change to displayed numbers. No collection on TEST sums above the 50K cap (Carrabba's is 56K but single-member, so it already sampled), so the new branch was never exercised end-to-end. `lib/entityFilter.ts` has no DB-mocking harness — its existing tests cover pure helpers only — and `computeEntityCounts` is private. The underlying `sampledEntityTermCounts` and `allocateSampleShares` are both proven elsewhere, so the risk is in the loop and the per-member scaling, not the primitives. **Either build a >50K multi-member collection on TEST and verify, or export the function and unit-test the branch, before this reaches customers.**

**⚠️ b. The lint ceiling was lowered on per-file evidence only.** 252 → 251, justified by one warning disappearing from a file I touched. `eslint .` OOMs locally, and a parallel session is committing concurrently, so the true repo total is unverified. **CI is the arbiter**; if it reddens, revert the number.

**c. Three migrations are applied to TEST but not production.** `sql/186/187/188`. Prod schema is three behind local, which is the direct cause of the §2 drift. `188` is inert (nothing calls it); `186` and `187` are live in code paths, so **pushing the app without migrating prod would break `/rows` and `/theme-counts`** — `p_drop_keys` and `sampled_theme_extras_page` would not exist. Migrate first, then push, or push nothing.

**d. Numbers move in two places.** The theme-cloud term percentages changed basis (verified correct, but anyone comparing to a screenshot from last week will see different figures), and entity counts for multi-member collections above the cap shift from exact to sampled.

**e. 29 commits this week carry `SKIP_SPEC_CHECK`.** Each is individually justified in its message, and the fresh drift run confirms only one genuine drift — so the bypasses were honest. But the volume is high enough to be worth noting rather than hiding.

## 6. Method notes worth keeping

Three predictions I made this week were wrong, all in the same direction — extrapolating from an isolated measurement to a real workload:

- Parallel keyset pages: predicted ~9×, got **28%**, and at concurrency 10 **every page hit the statement timeout**.
- Field projection: 34% payload reduction produced **11%** wall clock.
- Stratified sampling: a 5,000-row microbenchmark said **55×**; the real 50,000-row workload said **2.3×** (though the 1M test later vindicated the direction at 7.7×).

And one wrong conclusion from sound reasoning on a false premise: `vercel env pull` returned an empty Sentry DSN, so I concluded Sentry had never been switched on — while the product ships `/admin/sentry`, which would have answered directly.

The rule both of these point at: **measure the real path, and read the system rather than its configuration.**
