## 2026-05-15 (Thu) — Brand-match scoring on review-source search

- **Why:** user flagged that a brand search in the review-source wizard returns the real chain *plus* look-alikes — search "Chuy's" and you get the Tex-Mex chain alongside "Chuy's de Mexico", an unrelated business. The wizard auto-selected *all* results, so the junk got pulled into the dataset unless the user manually unpicked it. Asked for an intelligent way to rank strong vs. weak hits from the keyword alone.
- **`lib/brandMatch.ts` — pure, deterministic, no API cost.** `scoreBrandMatch(keyword, locations)` annotates each result with `matchScore` (0-100) + `matchStrength` and sorts strongest-first. Two signals: (1) **token similarity** — Dice coefficient between the location name and the keyword after dropping structural stopwords (`the`/`a`/`of`/…), so "The Capital Grille" still matches keyword "Capital Grille Boston"; (2) **chain consensus** — the largest cluster of identically-named locations *that is still keyword-relevant* is treated as "the brand", so a loose keyword ("Chuy's") still ranks the real chain ("Chuy's Tex-Mex") above look-alikes. A relevance floor (Dice ≥ 0.3) stops a big unrelated cluster from hijacking the ranking — verified by a test where a "Chuy's" search flooded with "Starbucks" still ranks Chuy's first.
- **Wired into the search route**, not the client — `app/api/review-sources/search` runs `scoreBrandMatch` on the DataForSEO results before returning, for both Google and Tripadvisor. Response type is now `ScoredLocation[]`.
- **Wizard UX:** `GoogleReviewsWizard` pre-selects only `'strong'` matches (falls back to selecting all if nothing scored strong, so the user is never stuck with an empty selection), and badges `'weak'` rows with an amber "Weak match" pill in both the selected and available panes. The existing split-pane (selected on top, available below) already separates them visually; the badge explains *why*.
- **Built in an isolated worktree** (`feature/brand-match-ranking`, branched from current `main`) — a second session is actively committing the brand-collection thread, so this stays off the shared working tree until a clean merge-back. 7 unit tests in `tests/unit/brandMatch.test.ts` cover exact match, look-alike, chain consensus, "The"-prefixed single location, total mismatch, sort order, and the unrelated-cluster guard.
