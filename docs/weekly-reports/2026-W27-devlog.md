## 2026-06-29 — PulseIQ round-based pacing — Phase 4: participant hold screen (pilot complete)

Closes the pilot (P1–P4). The chat response gains a `round_hold` flag (set only on the round-hold standby branch, so it's distinguishable from the disengagement "chill" standby that shares source='standby'). In the participant widget (pi/[id]/TownHallChat.tsx), when round_hold arrives the bot bubble is suppressed and a branded hold card renders in place of the input ("⏸️ … Waiting for the next item…"), while a useEffect polls POST /api/townhall/resume/[sessionId] every 4s. The resume endpoint is deliberately isolated from the 800-line shared chat handler (which serves every PulseIQ session) — no AI/clarifier/deflection, just the shared pickNextTopic over the participant's undiscussed active topics: while the moderator hasn't advanced (round still active, all discussed) it returns {holding:true}; once the moderator's Start-Round-N has completed the prior round and activated the next, pickNextTopic finds the new round's topic, the endpoint inserts it as a real bot turn (user_message null → not response-counted until answered) and returns it; the widget drops the hold card, appends the question, and the participant's next answer threads onto that turn via the normal chat flow. Turn-budget guarded; final round (no paused rounds left) falls through to the engine wrap-up/closing. Open mode untouched (round_hold never set). WHY: "participants placed on hold between items" is the core of the client's ask — a real hold card + auto-resume beats a bare standby bubble. Pilot note: resumed question served verbatim (no AI "next item" transition). tsc clean (clean-cache), 1059 tests, eslint warnings-only. Next: Phase 5 round-grouped exports.
